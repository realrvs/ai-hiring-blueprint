🗺️ Blueprint: AI-driven Recruitment (Hiring Automation)

Версия: 2.0 (Production-Ready)
Статус: Готов к утверждению на C-Level / ИТ-Архитектурном совете. Внедрение в enterprise-контуре с требованиями импортозамещения, 152-ФЗ, контроля затрат и Right to be Forgotten.

---

📖 О документе

Этот Blueprint описывает корпоративный стандарт автоматизации найма с AI-усилением через три фазы зрелости. Это не «список HR-инструментов» и не «идеалистическая схема». Это операционная система для AI-driven Recruitment, которая:

· Считает деньги (Cost per Hire, Compute Units, TCO).
· Контролирует latency (фоновые vs интерактивные агенты).
· Защищает данные кандидатов (152-ФЗ, Two-Way Masking, Purge Pipeline).
· Управляет согласиями (Consent Layer, TTL, Right to be Forgotten).
· Управляет изменениями (Fast-Track, Hotfix, обратные связи).
· Улучшается с каждым закрытием вакансии (Feedback Loop).

---

🎯 0. Три фазы автоматизации найма

Фаза Название Суть Уровень автономии Ключевая метрика
Фаза 1 Assist AI помогает рекрутёру, решения принимает человек Human-in-the-Loop Time-to-Screen
Фаза 2 Augment AI ведёт процесс, человек валидирует на контрольных точках Human-on-the-Loop Time-to-Interview
Фаза 3 Autonomous AI закрывает вакансию end-to-end, человек — только финальный оффер Human-out-of-the-Loop (с аудитом) Time-to-Hire, Cost per Hire

Правило перехода: нельзя прыгнуть из Фазы 1 в Фазу 3. Каждая фаза — минимум 2 квартала с измеримыми метриками качества, 100% выполнением Purge SLA и отсутствием критических инцидентов (дискриминация, утечка ПДн).

🔄 2. Конвейер найма: этапы, артефакты, контроль

2.1. Схема конвейера

```
+----------+   +----------+   +----------+   +----------+   +----------+
|  INTAKE  |-->| SOURCING |-->| SCREENING|-->| INTERVIEW|-->|  OFFER   |
|  (заявка)|   |  (поиск) |   | (отбор)  |   | (оценка) |   | (оффер)  |
+----------+   +----------+   +----------+   +----------+   +----------+

                                                                    v
+----------+   +----------+   +----------+   +----------+   +----------+
|  ONBOARD |<--|  HIRED   |<--|  DECISION|<--|  DEBRIEF |<--| NEGOTIATE|
+----------+   +----------+   +----------+   +----------+   +----------+

ОБРАТНЫЕ СВЯЗИ: Reject | Reopen | Feedback | Escalation | Consent-Revoked
```

2.2. Этап 1: Intake (заявка на найм)

Параметр Значение
Агент GigaChat 3.5 Ultra, промпт «заявка → Job Description + Requirements»
Контекст Org chart, грейды, бюджет ФОТ, похожие вакансии, требования 152-ФЗ
Артефакт в Git hiring/req-YYYY-NNN.md + hiring/jd-YYYY-NNN.md
Точка контроля Нанимающий менеджер + HRBP утверждают JD
Обратный ход Если JD неполный → новый коммит, уведомление
Latency-класс Фоновый

Правило: JD — источник истины для скрининга. Изменение JD после старта скрининга требует пересмотра всех кандидатов.

2.3. Этап 2: Sourcing (поиск)

Параметр Значение
Агент Скрапер + LLM-ранжирование (обязательно с Two-Way Masking)
Контекст JD + Requirements + Источники (hh.ru, Habr Career, Telegram, рефералы)
Артефакт в Git hiring/sourcing-YYYY-NNN.md (список с score)
Точка контроля Рекрутёр валидирует топ-20
Обратный ход Если пул < N → расширение источников, новый sourcing
Latency-класс Фоновый

Правило: Sourcing без Two-Way Masking запрещён. Все резюме проходят токенизацию до LLM.

2.4. Этап 3: Screening (отбор) — с батчингом

Параметр Значение
Агент GigaChat 3 Lightning: скрининг + Scorecard, batch 5–10 резюме
Контекст Резюме (tokenized) + JD + Scorecard template
Артефакт в Git hiring/screen-YYYY-NNN.md + Scorecard в ATS
Точка контроля Рекрутёр подтверждает шорт-лист
Обратный ход Если кандидат отклонён → feedback в ATS
Latency-класс Фоновый

Правило: агент выдаёт риски («пробел в опыте», «несоответствие по стеку»), а не бинарное «подходит/не подходит». Финальное решение — за человеком.

Правило батчинга: default — 5–10 резюме на один системный промпт. Исключения — метка no-batch (C-level, уникальные роли).

2.5. Этап 4: Interview (оценка)

Параметр Значение
Агент Interview Kit Generator + Live Assistant (подсказки интервьюеру)
Контекст Scorecard + резюме (re-identified) + предыдущие этапы + компетенции
Артефакт в Git hiring/interview-kit-YYYY-NNN.md + записи scorecard
Точка контроля Интервьюер проводит, оценивает, фиксирует
Обратный ход Если оценка противоречива → debrief, новый раунд
Latency-класс Интерактивный (assist) + Фоновый (kit)

Правило: AI не принимает решение о найме. Только assist: генерация вопросов, фиксация ответов, сверка со scorecard.

2.6. Этап 5: Decision & Offer

Параметр Значение
Агент Offer Calculator + бенчмаркинг (GigaChat 3.5 Ultra)
Контекст Scorecard + грейд + рынок + бюджет
Артефакт в Git hiring/offer-YYYY-NNN.md
Точка контроля HRBP + нанимающий менеджер утверждают оффер
Обратный ход Если отказ → feedback loop + новый sourcing
Latency-класс Фоновый

⚡ 3. Fast-Track: формализация исключений

3.1. Схема маршрутов

```
                         +---------------------+
                         |   Входящая заявка   |
                         +----------+----------+

                    +---------------+---------------+
                    |               |               |
                    v               v               v
            +--------------+ +--------------+ +--------------+
            |  FULL CYCLE  | |  FAST-TRACK  | |   HOTFIX     |
            +--------------+ +--------------+ +--------------+
            | JD -> Sourcing| | Массовый    | | Критичная    |
            | -> Screening | | найм, >10    | | роль, C-level|
            | -> Interview | | позиций      | | P0           |
            | -> Offer     | |              | |              |
            +--------------+ +--------------+ +--------------+

                    v               v               v
            +--------------+ +--------------+ +--------------+
            |  Уникальные  | | Массовые    | | C-level,     |
            |  роли,       | | роли:       | | emergency,   |
            |  C-level,    | | support,    | | production   |
            |  редкий стек | | sales, QA   | | down         |
            +--------------+ +--------------+ +--------------+
```

3.2. Маршрут A: Full Cycle

Критерии: уникальные роли, C-level, редкий стек, >3 недель найма.

Артефакты: JD → Sourcing → Screening → Interview Kit → Offer + Self-Check Report.

3.3. Маршрут B: Fast-Track

Критерии (автоматическая проверка):

· Массовый найм (>10 позиций одного грейда).
· Стандартные роли (support, sales, QA).
· Шаблонный JD из библиотеки.

Артефакты: PR + Self-Check Report (сокращённый). Пропускаются: кастомный JD, глубокий sourcing (используется пул). Обязательно: батчинг резюме.

Активация: метка fast-track на заявке. Gitea Actions проверяет критерии. Если критерии не выполнены — метка снимается, заявка блокируется.

3.4. Маршрут C: Hotfix

Критерии: C-level, emergency-роль, production down.

Артефакты: PR + краткий Self-Check Report. Всё остальное — постфактум. Обязательно: Consent-проверка перед стартом.

Активация: только HRD или CEO. После закрытия — Post-Mortem с обязательным созданием JD/Scorecard, если проблема системная.

💰 4. Compute Units: универсальная метрика

4.1. Формула

```
1 CU = 1 GPU-час на RTX PRO 6000 (или эквивалент)

Для API-моделей:
1M токенов GigaChat Max = 0.65 CU

С батчингом (10 резюме / батч):
CU_total = CU_batch = 1.0 CU вместо 10.0 CU

```

Параметр Фоновый Интерактивный При превышении

              v                      v                      v

|                     УРОВЕНЬ 2: GigaChat 3 Lightning                         |
|                          (Edge / API)                                       |
+-------------------------------------+---------------------------------------+
                                      |
              +----------------------+----------------------+
              | error rate >10%      | latency >60s         |
              v                      v                      v
+-----------------------------------------------------------------------------+

|                          (Ручной рекрутинг)                                 |
+-----------------------------------------------------------------------------+
```

6.2. Критерии переключения

Критерий Порог Действие
Error rate 5% за 5 мин Переключение на Уровень 2
Latency 30 сек (p95) Переключение на Уровень 2
GPU utilization 90% Переключение на Уровень 2
Error rate 10% за 5 мин Переключение на Уровень 3
Latency 60 сек (p95) Переключение на Уровень 3

Circuit Breaker: если Уровень 1 недоступен >15 минут — circuit breaker открывается, все запросы идут на Уровень 2. Автоматически закрывается через 5 минут после восстановления.

Правило: Fallback — не «опция», а обязательный слой. Без него production-система не выживает.

🧪 7. Bias Detection: Diff-based

7.1. Механика

Параметр Значение
Запуск Асинхронно, после каждого этапа (не блокирует)
Область Только решения по кандидатам (по diff)
Fairness score Считается для изменённых решений
Накопленный score Отслеживается по репозиторию отдельно

7.2. Правила

1. Блокирующий порог: fairness score для изменённых решений <85% → заявка помечается bias-risk, требуется ручное ревью HRBP.
2. Накопленный score: если общий fairness score по репозиторию падает ниже 80% — создаётся задача tech-debt:bias-audit.
3. Инструменты: собственные проверки на age/gender/language bias + внешний аудит.

Почему это работает: Diff-based bias detection не блокирует процесс, но даёт точную картину fairness для новых решений. Накопленный score предотвращает незаметную деградацию.

🔐 8. Two-Way Masking: PII Scanning до LLM

8.1. Проблема

Классическое NER-маскирование необратимо удаляет PII, что приводит к:

· Потере смысла («<PERSON> работал в <ORG> над <PRODUCT>» — бесполезно).
· Ложным срабатываниям на редких технологиях / вузах.
· Невозможности показать рекрутёру полный контекст.

8.2. Решение: Anonymization / Re-identification Tokenizer

```
+-----------------------------------------------------------------------------+
|                    ANONYMIZATION TOKENIZER                                  |
|   PII -> Token (детерминированный) | Token Vault (on-prem, AES-256)         |
+-------------------------------------+---------------------------------------+
                                      |
                                      v
+-----------------------------------------------------------------------------+
|                         LLM GATEWAY (работает с токенами)                   |
|              Пример: "<CANDIDATE_NAME_1> работал в <COMPANY_1>               |
|                       над <PRODUCT_1> с использованием Rust + ML"           |
+-------------------------------------+---------------------------------------+
                                      |
                                      v
+-----------------------------------------------------------------------------+
|                    RE-IDENTIFICATION (только на стороне клиента)            |
|              Токены -> реальные значения в UI рекрутёра (RBAC-контроль)     |
+-----------------------------------------------------------------------------+
```

8.3. Правила

1. Детерминированность: один и тот же PII → один и тот же токен в рамках сессии.
2. Token Vault: хранится on-prem, шифруется (AES-256), доступ только у роли recruiter (RBAC).
3. Re-identification: только в UI рекрутёра. LLM никогда не видит реальные PII.
4. Audit: каждое демаскирование логируется (кто, когда, какой токен).
5. Fallback: если Tokenizer недоступен — система работает в режиме read-only, новые скрининги блокируются.

8.4. Порядок действий

```
1. Pre-commit hook: PII-детектор (локально, у рекрутёра)
2. Gitea Actions (
